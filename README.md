# ORC Document Automation

A document automation application built with React, Node.js/Express, MySQL, local file storage, and open-source PDF tooling.

## What Works

- Register/login with admin/client roles
- Upload a PDF template to local storage
- Run local PDF text/layout detection for likely fields
- View the PDF in a React editor
- Add, drag, resize, rename, require, and delete fields
- Save template fields once and reuse them
- Generate a custom data-entry form from saved fields
- Fill the uploaded PDF using submitted form data
- Preview highlighted fields and download generated PDFs
- Upload CSV/XLSX spreadsheets, map columns to fields, and bulk generate PDFs
- Generate PDFs through `POST /api/templates/:id/generate/api`
- Store originals and generated files in separate local folders

The detection step uses local PDF text/layout extraction through `pdfjs-dist`. No AWS Textract, Azure Document Intelligence, Google Vision, OpenAI API, paid OCR, or external OCR service is used.

## Tech Stack

- Frontend: React, Vite, pdfjs-dist, lucide-react
- Backend: Node.js, Express, Multer
- Database: MySQL 8 through mysql2
- PDF generation: pdf-lib
- Spreadsheet parsing: xlsx
- Storage:
  - Original PDFs: `server/uploads/originals`
  - Generated PDFs: `server/uploads/generated`
  - Temporary spreadsheets: `server/uploads/spreadsheets`
  - Central and per-firm data: MySQL

## Local Setup

```bash
npm install
npm run setup
npm run db:check
npm run seed
npm run dev
```

`npm run setup` creates `.env` with a random JWT secret when one does not
already exist, and prepares the local data/upload directories. It never
overwrites an existing `.env` file. Start MySQL first and set `MYSQL_URL` in
`.env`. The MySQL account must be allowed to create databases because each firm
receives an isolated MySQL schema.

Then open:

```text
http://localhost:5173
```

Demo login after seeding:

```text
Email: demo@example.com
Password: password123
```

The Express API runs on `http://localhost:4000`. Vite proxies `/api` to the backend during development.

## Production-Style Local Run

```bash
npm run build
npm start
```

Then open:

```text
http://localhost:4000
```

## Docker Deployment (recommended)

The Docker image builds the React app and serves it from the same Express
server as the API. Compose starts MySQL 8 as a second service. MySQL data and
uploaded files are kept in separate named volumes so they survive upgrades.

```bash
npm run setup
docker compose up -d --build
```

Open `http://localhost:4000`. Check the deployment and its database connection
with:

```bash
curl http://localhost:4000/api/health
docker compose ps
docker compose logs -f app
```

To add the optional demo user and sample document inside Docker:

```bash
docker compose run --rm app npm run seed
```

For a public server, set `CLIENT_ORIGIN` in `.env` to the public application
URL (for example `https://documents.example.com`) and place a TLS reverse proxy
in front of port 4000. Set `APP_PORT` in `.env` if the host should expose a
different port. Production startup is rejected when `JWT_SECRET` is missing or
still contains the example value. Never commit `.env`.

### Updating a Docker deployment

```bash
git pull
docker compose up -d --build
```

Do not remove `mysql-data` or `app-storage` unless you intentionally want to
delete database data or uploaded documents.

## Railway Deployment

1. Add a Railway MySQL service to the project.
2. In the application service, add `MYSQL_URL` as a reference to the MySQL
   service's `MYSQL_URL` variable (commonly `${{MySQL.MYSQL_URL}}`).
3. Set `NODE_ENV=production`, a strong `JWT_SECRET`, and `CLIENT_ORIGIN` to the
   generated application domain.
4. Attach an application volume at `/app/storage` for uploaded/generated files
   and set `RAILWAY_RUN_UID=0` so the container can write to it.
5. Keep the service at one replica unless file storage is moved to shared
   object storage. `railway.json` already configures the Docker build, health
   check, graceful draining, and restart policy.

The MySQL service persists the database, so the application volume is only for
uploaded and generated files. The application uses Railway's injected `PORT`.

## Environment and Database

Copy `.env.example` manually or use `npm run setup`. The important settings
are:

| Variable | Purpose | Local default |
| --- | --- | --- |
| `JWT_SECRET` | Signs login tokens; use a long random value | Generated by setup |
| `CLIENT_ORIGIN` | Browser origin allowed to call the API | `http://localhost:5173` |
| `MYSQL_URL` | MySQL connection URL with schema-creation permission | See `.env.example` |
| `MYSQL_SSL` | Enables TLS options for providers that require it | `false` |
| `UPLOADS_DIR` | Persistent uploaded/generated documents | `server/uploads` |
| `PORT` | Express API/application port | `4000` |
| `MAX_UPLOAD_MB` | Maximum uploaded file size | `25` |

A MySQL server is required. The central schema and each firm's isolated schema
are created automatically. Docker Compose supplies MySQL locally; Railway's
managed MySQL service supplies it in production. The health endpoint returns
`database: "connected"` only after a real MySQL query succeeds.

## API Routes

```text
POST   /api/auth/register
POST   /api/auth/login
GET    /api/dashboard
POST   /api/templates/upload
GET    /api/templates
GET    /api/templates/:id
GET    /api/templates/:id/pdf
POST   /api/templates/:id/fields
PUT    /api/templates/:id/fields/:fieldId
DELETE /api/templates/:id/fields/:fieldId
POST   /api/templates/:id/generate/form
POST   /api/templates/:id/spreadsheet/preview
POST   /api/templates/:id/generate/spreadsheet
POST   /api/templates/:id/api-key
POST   /api/templates/:id/generate/api
GET    /api/documents
GET    /api/documents/:id
GET    /api/documents/:id/download
```

Most routes require a JWT bearer token from login. The API generation route also accepts an `x-api-key` created for that template.

Example API generation request:

```bash
curl -X POST http://localhost:4000/api/templates/1/generate/api \
  -H "Content-Type: application/json" \
  -H "x-api-key: orc_live_your_key_here" \
  -d '{"client_name":"Taylor Morgan","email":"taylor@example.com","approved":true}'
```

## Notes

- Field coordinates are stored in PDF points with a top-left origin in the editor. The backend converts them for `pdf-lib`, which uses a bottom-left origin.
- Scanned-image PDFs will need a local OCR renderer/Tesseract enhancement for stronger automatic detection. The MVP still supports manual field setup for any PDF that renders in the browser.
- Uploaded and generated documents are never placed in public static folders. They are streamed through authenticated API routes.
